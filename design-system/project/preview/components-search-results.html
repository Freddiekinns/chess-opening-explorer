What replaces components-search-hub once two characters are typed — on all three surfaces. One ranked list that scrolls, no reveal button. Fuzzy matching already absorbs typos, so there is no "did you mean", no correction notice and no explanation of what was understood: the right openings appearing is the feedback. Natural-language queries ("aggressive openings") land in this same list — the server's style intent changes the ranking, not the layout.

This card owns the panel, not the rows. Rows come from components-search-row, the same row the hub draws. They were two separate implementations until 2026-07-30 — on two different type scales — so typing a second character redrew every opening at a different size, weight and layout. There was a third in the top bar. Do not restyle a row here to suit the results.

The list scrolls further than it used to. It was capped at 280px against rows of 71px, so under four of twenty results were visible and the panel read as a peephole. It now scales with the viewport (min(60vh, 480px)), which is around nine rows on a laptop.

No count line, and no number anywhere. An earlier draft put "14 openings match" above the list. It was cut once the number turned out to be unusable: the search counts every record scoring above zero, which for "sicilian" is 4,269 against a family of roughly 1,710. Anyone reads that as a claim about how many Sicilians exist. Counting only the rendered rows instead would have been true but useless — it always says twenty. A count that cannot be trusted and a count that never varies are both worse than the silence the page already had.

Surprise me sits outside the scroller, and keeps its hint on every surface. It used to vanish on the second keystroke — the way out of a search that is not working disappearing exactly when the user is flailing. Twenty results deep is where someone gives up, so that is where it has to still be on screen; it is reachable by arrowing one past the last result, not only by clicking. The top-bar dropdown used to drop the visible hint for want of ~25px and keep it only in a title and an aria-label — invisible to a sighted user arrowing through the list. That panel now sizes to its contents instead: the row explains itself, and the exception is gone.

"Saved", not a star. Repertoire membership rides on the result row rather than sitting in a section of its own — a saved opening that also matched the query would otherwise be drawn twice, at two different ranks. It is a text badge because everywhere else in the app a star is a control you press to add or remove; on a row whose whole job is to navigate, the same star would invite a tap that does something else entirely.

Saved openings also win ties. The badge was the visible half of the idea; the ranking is the useful half. Between two matches the search cannot separate — a move query returns dozens on an identical score — the opening already in the repertoire goes first. Only within a tie: a weak match you happen to have saved is still a weak match, and floating it over twenty better ones would make search worst for the people most invested in it. The band is relative (within 2% of the leader) because score scales differ by an order of magnitude between search types.

One dead end, one voice. There were two strings and a silence: the hero said "Try a different spelling, ECO code (e.g., B90), or abbreviation (e.g., QGD)", the mobile overlay said the copy above, and the top-bar dropdown simply closed — so a failed search on desktop looked identical to not having typed. The overlay's survived: it points somewhere the user can go, and it does not teach them the word "abbreviation" at the moment they have just failed. Two example ECO codes for the same advice was the other half of the tell. Note the hint is only true because the server gained an ECO branch at the same time — before that, "try an ECO code" returned nothing on any surface without a local index.
